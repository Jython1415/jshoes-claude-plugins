# Triage

Assess the current state of the project and propose what to work on.
This is a research and synthesis task -- you are not implementing
anything, you are helping the user decide where to focus.

## Arguments

- `--light`: Single-agent Haiku pipeline. One Haiku subagent runs all
  five steps (data gathering, scoring, and presentation). The boolean
  checklists in Step 4 are designed for Haiku-level execution. Use for
  cost-sensitive triage runs.

## Step 1: Repo state

Gather context on what's been happening recently:

1. `git log --oneline -20` -- recent commits, what landed recently
2. `git branch -a` -- any open feature branches
3. `gh pr list` -- open PRs awaiting review or merge
4. `gh run list --limit 5` -- recent CI status (if CI is configured)

Note anything that needs immediate attention (failing CI, stale PRs,
unfinished branches).

## Step 2: Open issues

Fetch all open issues:

    gh issue list --state open --limit 50 --json number,title,labels,createdAt,updatedAt

For each issue, understand:
- What it's asking for
- How long it's been open
- Whether it has labels indicating priority or category
- Any comments with additional context

If the issue list is large, fetch full details for the most promising
candidates:

    gh issue view <number> --json title,body,labels,comments

## Step 3: Recent context

Check for session continuity signals. Consult the project's documentation
(CLAUDE.md, DEVELOPMENT.md, or equivalent) to learn where prior session
context, handoff notes, or activity logs are stored. Look for:

1. Handoff notes or task lists from prior sessions
2. Memory files or session summaries with open issues tracking
3. Recent session logs or activity patterns (recurring failures,
   incomplete work)

## Step 4: Score and rank

For each open issue, run the **priority checklist** and **effort
classification** below. Do not skip signals or improvise criteria --
apply the checklist mechanically.

### Priority checklist

Answer each question YES or NO for each issue. Each YES adds the
listed points.

| Signal | Points | How to verify |
|--------|--------|---------------|
| Blocks other issues? | +3 | Another open issue explicitly depends on this one, or this issue modifies shared code that a later issue needs. Thematic similarity alone does NOT count. |
| Is a regression or breakage? | +3 | Something that previously worked is now broken. Check recent commits and CI. |
| Has clear acceptance criteria? | +1 | The issue body specifies what "done" looks like (concrete deliverables, not vague goals). |
| Has been open > 30 days? | +1 | Check the `createdAt` field. |
| Has label indicating priority? | +1 | Labels like `priority`, `urgent`, `critical`, `bug`, or milestone assignment. |
| Requested by user or external? | +1 | Filed by a human (not auto-generated by a session). Check the author. |
| Enables multiple follow-up issues? | +2 | Completing this issue unblocks 2+ other open issues. Verify by checking issue cross-references. |

**Priority score** = sum of points (0--12).

### Effort classification

Classify each issue as **S**, **M**, or **L**:

| Size | Criteria |
|------|----------|
| **S** | Touches 1--2 files. Mechanical change (typo, config, single-line fix). No design decisions. |
| **M** | Touches 3--6 files or requires moderate design work. Fits in one PR with one review cycle. |
| **L** | Touches 7+ files, requires architectural decisions, or needs splitting into multiple PRs. |

When unsure between two sizes, pick the larger one.

### Dependency verification

Before claiming issue A blocks issue B, confirm at least one:

- [ ] A modifies files that B also needs to modify (overlapping changes)
- [ ] B's implementation requires code that A will introduce
- [ ] Merging both independently would create a merge conflict

If none apply, the issues are **independent**. Thematic similarity
(both are "performance", both are "docs") is NOT a dependency.

### Bundleable vs independent

Issues are bundleable only when one of the dependency verification
checks above passes. When in doubt, default to independent. Smaller,
focused PRs are easier to review and revert.

### Rank order

Sort issues by:
1. Priority score (descending)
2. Effort as tiebreaker: S before M before L (prefer quick wins at
   equal priority)

## Step 5: Propose

Present a **prioritized session queue** -- an ordered list of work items,
where each item is either a single issue or a bundle of related issues.

Use this template for each queue item:

    ### [Rank]. #<number>: <title>
    - **Priority score**: <N>/12 (<list which signals were YES>)
    - **Effort**: S / M / L
    - **What it unblocks**: <what becomes possible after this is done>
    - **Bundle**: <if bundled, list other issue numbers and the concrete
      bundling reason -- overlapping files, blocking dependency, etc.>
    - **Why this rank**: <1 sentence explaining the ranking decision>

After listing all items, lead with your recommendation for what to
tackle first. Explain why and surface the trade-offs (e.g., "Issue X
scores highest but is size L; issue Y is close behind and size S -- the
user could ship Y quickly first").

Flag issues you'd skip this session and why:
- Issue lacks acceptance criteria AND has no comments clarifying intent
- Issue is a vague future idea with no concrete deliverable
- Issue duplicates or is superseded by another open issue

## Guidelines

- **Delegate the research.** Use subagents for fetching issue details
  and exploring the codebase. Keep the main context for synthesis and
  presentation. If `--light` was passed, use a single Haiku subagent for
  all five steps. Otherwise, use a single Sonnet subagent for all steps.
- **Apply the checklist mechanically.** The priority signals and effort
  criteria exist so scoring is consistent. Do not override the checklist
  with subjective judgment. If the checklist ranking feels wrong, note
  the tension in "Why this rank" but keep the score-based order.
- **Be opinionated.** The user wants your recommendation, not a menu.
  Say what you'd pick and why.
- **Note what you'd skip.** Use the explicit skip criteria above. Not
  everything needs to be tackled now.
